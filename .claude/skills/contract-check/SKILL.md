# 契約書チェック

契約書レビューで本当に役に立つかどうかは、「その条項があるか」ではなく「**その条項がどう書かれているか**」を見られるかで決まる。`損害賠償の定めあり ✓` は何も言っていないに等しい。上限がなく間接損害まで含む賠償条項なのか、委託料を上限とする条項なのかで、依頼者が負うリスクは桁違いに変わる。このスキルは一貫して、条文を引用し、その書きぶりが依頼者にとってどちらに傾いているかを判定することを求める。

もうひとつの軸が、**書かれていないこと**の検出。実務上の紛争の多くは、禁止条項ではなく空白から生まれる。検収の定めがない、契約不適合責任の期間が決まっていない、知的財産権の帰属が書いていない——こうした欠落は読んでいて気づきにくいので、類型別チェックリストと突き合わせて機械的に洗い出す。

法令の確認は記憶に頼らない。法令名・条番号・要件は改正で変わる（例：下請法は2025年改正で「中小受託取引適正化法」に改称され2026年1月1日施行）。条文を引用するときは必ず `scripts/egov.py` で現行条文を取得すること。

## 進め方

### 1. 契約書を読み込む

- `.pdf` → `pdf` スキル、`.docx` → `docx` スキルで本文を抽出する。画像PDFならOCRが必要になる旨を伝える。
- 貼り付けテキストや `.txt` / `.md` はそのまま読む。
- 全文を読むこと。長さを理由に抜粋で済ませると、末尾の管轄条項や附則に埋め込まれた不利条項を見落とす。

### 2. 立場を確認する

不利・有利の判定は立場が決まらないと成立しないので、**レビュー前に必ず確認する**。AskUserQuestion で聞く:

- 受注者側（業務を受ける／物を売る／借りる側）
- 発注者側（業務を出す／物を買う／貸す側）
- 中立（双方のリスクを対称に列挙）

依頼文や契約書の甲乙表記から立場が明らかな場合（「うちが受託する側で」等）は、推定した立場を一文で提示して確認を取るだけでよい。確認なしに推測で進めると、レビュー全体の結論が逆向きになる。

質問できない状況（非対話実行、サブエージェントとして動いている等）では止まらずに進める。依頼文と契約書から立場を推定し、**レポートの冒頭に「立場を〈受注者側〉と推定して作成した。異なる場合は結論が変わる」と明記**したうえで通す。どちらとも読めない場合は中立で作成する。

### 3. 契約類型を判定し、対応するチェックリストを読む

表題ではなく**実態**で判定する。「業務委託契約書」と題しながら成果物の完成と引換えに報酬を払う内容なら請負であり、契約不適合責任や641条の解除など請負のルールが効く。判定した類型と根拠を依頼者に一言伝える。

| 類型 | 読むファイル |
|---|---|
| 業務委託・請負・準委任・SES・保守 | `references/type-gyomu-itaku.md` |
| 雇用契約・労働条件通知書・就業規則関連 | `references/type-employment.md` |
| 秘密保持契約（NDA） | `references/type-nda.md` |
| 売買・継続的取引基本契約・OEM | `references/type-sales.md` |
| 賃貸借（不動産・動産・リース） | `references/type-lease.md` |
| ライセンス・SaaS利用規約・共同開発 | `references/type-license.md` |

どの類型でも **`references/checkpoints-common.md`（全契約共通の不利条項パターン）は必ず読む**。類型ファイルはその上乗せ分。複数類型の複合契約（例：開発＋保守＋ライセンス）なら該当ファイルを全部読む。

### 4. 条項を棚卸しする

まず全条項を「条番号 / 見出し / 何を定めているか一行」で一覧にする。これを土台にすると、欠落チェックが漏れなく回せるうえ、レポートで条番号を取り違えなくなる。定義条項・別紙・個別契約への委任がある場合は、その参照先が実在するかも見る（別紙が存在しない、個別契約で定めるとしか書かれていない、は頻出の穴）。

### 5. 内容を評価する

チェックリストの各項目について、次のどれかに分類する:

- **不利** — 依頼者の立場から見て一方的、または相場から外れている
- **要確認** — 書きぶり次第で不利になる、事実関係を確認しないと判定できない
- **妥当** — 特段の問題なし
- **欠落** — 定めがない

「不利」「要確認」「欠落」に該当したものだけをレポートに載せる。妥当なものは件数だけ示せば十分で、全条項の逐条解説はノイズになる。

判定にあたっては必ず**原文を引用**する。引用できない指摘は、その時点で根拠がないということ。また、片面性（甲だけが解除できる、乙だけが賠償義務を負う）は最も検出しやすく効きやすい不利条項のパターンなので、条項ごとに「これは双方向か」を必ず見る。

### 6. 法令に当たる

条文や法定の数値基準に言及するときは、記憶で書かずに取得する。

```bash
python3 scripts/egov.py laws                  # 頻出法令のID一覧
python3 scripts/egov.py search 労働者派遣      # 法令名から law_id を探す
python3 scripts/egov.py article 民法 641       # 条文を取得（枝番は 398-2）
python3 scripts/egov.py keyword 秘密保持       # 条文本文の全文検索
```

使い分けと調査の型は `references/legal-sources.md` に書いてある。指定の3サイトの役割は次のとおり:

- **e-Gov法令検索** <https://laws.e-gov.go.jp> — 現行条文の一次情報。上のスクリプトが叩いているのがこれ。条文を引用するときの出典はここ。
- **日本法令索引** <https://hourei.ndl.go.jp/#/> — 改正沿革・制定経緯。「この条文はいつの改正で入ったか」「旧法ではどうだったか」を確認するときに WebFetch で参照。
- **厚労省 労働契約ポータル** <https://roukeiseminar.mhlw.go.jp/rules.html> — 労働契約法・労基法の行政解釈と裁判例。雇用契約をレビューするときは条文だけでなくここの解説（契約の締結／労働条件の変更／契約の終了／無期転換）も当たる。

ネットワークが使えずスクリプトが失敗した場合は、**推測で条文を書かない**。「条文未確認」と明記し、確認すべき法令名と条番号だけを示す。誤った条文番号を添えた指摘は、指摘がないより有害。

### 7. レポートを出す

`references/report-format.md` のテンプレートに従って作成し、

1. 会話に**サマリーと🔴高リスク指摘**を表示する（🔴が5件を超えるときは上位5件まで。依頼者が最初に知りたいのはここ）
2. 全文を Markdown ファイルに保存する。保存先は契約書と同じディレクトリの `契約書チェック結果_<契約書名>_<YYYYMMDD>.md`。書き込めない場所ならスクラッチパッドに保存してパスを伝える。
3. **同梱のレンダラでHTMLに変換する。** 閲覧・共有・印刷はこちらが本体になる。

```bash
python3 scripts/render_report.py "契約書チェック結果_業務委託契約書_20260921.md"
```

同じ場所に `.html` が出る。HTMLを自分で書き起こさないこと——レンダラを通せば、リスク階級の色分け、絞り込みボタン、目次、修正案のコピーボタン、印刷用レイアウトが毎回同じ品質で付く。単一ファイルで外部依存がないので、そのままメール添付でも社内共有でも開ける。

最後に、依頼者には **HTMLのパスを先に伝える**（Markdownは差分管理・再編集用として併記する）。契約書は機微な情報なので、HTMLはローカルファイルとして渡し、こちらから外部にアップロードしたり公開したりしない。依頼者が共有を望む場合も、ファイルを渡すところまでに留める。

## 指摘の書き方

指摘は「原文 → 何が問題か → 現実に何が起きるか → 修正案」の順で書く。抽象論で終わらせず、依頼者がその場面を想像できるところまで具体化する。

**悪い例**

> 第12条の損害賠償条項は乙に不利です。修正を検討してください。

**良い例**

> **[R-02] 第12条（損害賠償） 🔴 高**
>
> > 第12条 乙は、本契約に関して甲に損害を与えた場合、その一切の損害（逸失利益、第三者からの請求に基づく損害を含む）を賠償する。
>
> - **問題**: 賠償額に上限がなく、通常は除外される逸失利益・間接損害まで含む。しかも甲側の賠償義務は定められておらず片面的。
> - **起こり得る事態**: 委託料60万円の案件で、納品物の不具合により甲のECサイトが1日停止した場合、その日の売上相当額（数百万円規模）を逸失利益として請求され得る。受託金額と賠償リスクが釣り合わない。
> - **法的根拠**: 民法416条の通常損害・特別損害の区分を契約で上書きしている状態。消費者契約でないため無効にはならず、そのまま効力を持つ（民法416条／e-Gov: https://laws.e-gov.go.jp/law/129AC0000000089）。
> - **修正案**: 「乙の賠償責任は、故意又は重過失による場合を除き、本件業務の委託料相当額を上限とし、逸失利益及び間接損害を含まないものとする。甲についても同様とする。」

指摘の量は階級で変える。🔴はこの密度で書き、🟡は原文引用・問題・修正案の3点に絞り、🔵は一行＋確認事項にとどめる。全部を同じ密度で書くと、件数が多い契約では🔴が埋もれて逆に伝わらなくなる（詳細は `references/report-format.md`）。

リスク階級の基準:

- 🔴 **高** — 法令違反、無効・不成立のおそれ、金額・期間が無限定、明白な片面条項。締結前に必ず交渉すべきもの。
- 🟡 **中** — 相場から外れているが交渉で戻せる、または解釈が分かれて紛争の火種になるもの。
- 🔵 **低** — 実務上は許容範囲だが、認識しておくべきもの。

欠落の指摘も同じ粒度で書く。「〜の条項がありません」だけでは動けないので、**その空白を誰がどう突いてくるか**まで書く。例：検収条項がない場合、「納品後いつまでも『まだ確認中』と言われて報酬支払期日が起算されない」「どこまで直せば完成なのか決まらず無限に修正対応が続く」。

## やらないこと・伝えること

- これは法的助言ではない。レポート末尾に「最終的な判断は弁護士に確認してください」を必ず入れる。リスクが高い契約（高額、長期拘束、知財の全面譲渡、個人保証、専属的な競業避止）では、本文のサマリーでも弁護士相談を勧める。
- 条文の解釈が分かれる論点では、断定せずに「A説・B説があり、この書きぶりだとB説で解釈されるおそれがある」と幅を示す。
- 依頼者が「発注者側」でも、受注者側の法令上の保護規定（取適法・フリーランス法・労基法）に触れる条項は**自社の法令違反リスク**として必ず指摘する。立場に有利だからといって違法な条項を黙認しない。
- 契約書の全文を書き換えた版を勝手に作らない。指摘ごとの差し替え文言までに留め、全面改訂が必要なら依頼者に確認する。
